# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

PhysiQ-Assessment is a musculoskeletal physiotherapy clinical assessment assistant. It guides clinicians through a structured 5-phase workflow (phases 1–4b–5, where 4b is a sub-phase of 4) using evidence-based screening, ICF decision trees, and diagnostic likelihood ratios. It is in active clinical pilot use.

**Deployment:** Push to `main` triggers `deploy-to-hub.yml`, which copies the app files into the central PhysiQ hub repo (`physiodevapp/physiq`). The hub's own GitHub Pages deployment serves the app at `physiodevapp.github.io/physiq/assessment/`. There is no standalone Pages deployment for this repo — but the deployed copy at that URL is itself a complete, installable PWA independent of the hub (see "Standalone use" below); "no standalone Pages deployment" only means physiq-assessment doesn't have its *own* separate GitHub Pages site.

### Standalone use (without the hub)

`manifest.json` (`start_url`/`scope`: `/physiq/assessment/`, `display: standalone`, install icons) plus `sw.js` already make the deployed app fully installable on its own — no code changes needed. Open `https://physiodevapp.github.io/physiq/assessment/` directly (not through the hub) and use the browser's "Install app" / "Add to Home Screen"; it installs as its own icon, scoped to that path, separate from the hub's own installed PWA. `_initHubIntegration()` (`app.js`) no-ops cleanly outside an iframe (`window.self === window.top`), so nothing hub-specific blocks standalone use. What's unavailable standalone (both are hub-only by design, not bugs): the hub's audio recording widget, and the "navigate to physiq-report" hop from phase 5. In exchange, standalone phase 5 has its own **«🎙 Informe con IA» card** (record/attach audio → narrative CIF report via the physiq-report orchestrator worker; see "Informe narrativo con IA (standalone)" below), which never loads in the hub. Phase 5's bottom «📤 Compartir» works either way; only its «Enviar al informe» option is hub-only (see "Phase 5 and finalizarValoracion()" below). Session data (IndexedDB, `BroadcastChannel`) is scoped per browser *origin*, not per path, so a standalone install and the hub-embedded copy share the same session data when used in the same browser.

## Development

No build step, no package manager, no dependencies. The app runs as static HTML/CSS/JS.

To develop locally, serve from the root with any HTTP server:
```
npx serve .
```
Or use VS Code Live Server. Open `index.html` directly in a browser also works for most features.

There are no linting or compilation commands. To run unit tests:
```
node tests/unit.js
```

**Browser smoke test** (`tests/smoke.mjs`, optional dev tool — not a project dependency, needs Playwright available separately): launches the real app with Playwright and checks the things `tests/unit.js` can't — that every ES module actually loads (200, no broken `import` across `app.js`/`state.js`/`data.js`/`data/*.js`/`phase4.js`/`phase4b.js`/`lib/session.js`), no console/page errors, and a full click-through of phases 1–5 (one golden path per region — always the first option at each CIF tree step, not every branch — but for **all 7 regions**, since each has its own `CIF_TREES` entry with a different step count/branches) plus the mobile "☰ Fases" button via the real UI. Run it after any change touching module structure, `window` exposure, or navigation — and always after editing `CIF_TREES` for any region, since this is the only check that exercises real rendering (`renderStep`/`checkTreeComplete`/`showTreeComplete`), which `tests/unit.js` cannot (see below). Some behaviours (confirm dialogs, clearing the session, what phase 5 never folds) are only checked here. **CI** (`.github/workflows/tests.yml`, user decision 2026-10) runs `node tests/unit.js` and the full smoke test on every PR to `main` (Playwright installed only in the runner; the repo still has no dependencies): changes reach `main` through a PR, merged only with that check green, so a session doesn't need to run the full smoke itself — run it locally only to reproduce a CI failure:
```
npx serve . &
node tests/smoke.mjs                # add http://localhost:PORT if not :3000 (~1.5 min)
node tests/smoke.mjs --lista        # section ids
node tests/smoke.mjs --solo tejidos,fase5   # only the sections your change touches (seconds)
```
In a session, run only the sections related to the change with `--solo` (the result line then says «PARCIAL») and leave the full run to the PR's CI. Sections run 3 at a time and the per-region walks 7 pages at a time, each in its own browser context (`--secciones N`, `--paralelo N`; `1` for both runs fully serially if a failure looks timing-related); each section's output is printed whole, in list order, with its time. A new check is a new entry in `SECCIONES` (own page from `ctx`, never state left by another section). A section that reads what the app copied calls `portapapelesPropio(context)` (never `grantPermissions(['clipboard-…'])`): Chromium has one clipboard for the whole browser, so with sections in parallel one read what another copied (intermittent `plan-ia` failure, 2026-10). Prefer waiting for a condition (`waitForSelector`/`waitForFunction`) over `waitForTimeout`, and never read an element that may not exist with `page.textContent(sel).catch(…)`: it waits the full 30 s default timeout first (that alone cost 30 s per run, 2026-10).
Open the app with `abrirApp(page)` (it `goto`s `BASE_URL` and waits until `window.goToPhase`/`window.state` exist), never a bare `page.goto(BASE_URL)`: `networkidle` doesn't mean the modules ran, and when one module request is lost (seen twice in full runs right after starting `npx serve`, 2026-10) the app never boots — the old symptom was a 30 s click timeout plus «state/selectOption/goToPhase is not defined»; now the section fails at once naming the failed request. No retry on purpose. If it happens, re-run the full test; if it repeats with the same file, it isn't the server.
If Playwright isn't resolvable via a normal `import`, it also tries `createRequire` so a global-only install (found via `NODE_PATH`) still works — Node's ESM resolver ignores `NODE_PATH` on its own.

**Editing `CIF_TREES` (adding/reorganizing a region's decision tree):** inserting or reordering a `step` inside a region's array can silently change which step an *untouched* option falls through to — `next: null` resolves positionally to `steps[idx+1]` (see the schema comment above `CIF_TREES` in `data.js`; each region's tree is `export const tree` in `data/<region>.js`). `node tests/unit.js` guards this with a checked-in navigation snapshot (`tests/fixtures/cif-tree-navigation.json`). After editing a tree: run `node tests/unit.js`; if it fails on "CIF tree navigation regression", read the diff and confirm every changed entry is an intended part of your edit, not collateral from reordering `steps[]`; only then run `node tests/gen-cif-snapshot.mjs` to regenerate the fixture (see that file's header), re-run `node tests/unit.js` to confirm, and commit the regenerated fixture together with the `data/<region>.js` change. Full rationale in `MIGRATION_PLAN.md`, Fase C.

**Editing a phase 4b test's `criterio`:** the visible `criterio` is kept short (technique, positive criterion, bedside cautions) and the rest lives in `razonamiento.detalle`, shown in the «Ampliar →» panel (see "Phase 4b «¿Por qué?»" below). `node tests/unit.js` guards that nothing is lost when moving text: `tests/fixtures/criterios-4b.json` holds every chunk of every test's text (cut after «.», «;», «:» by `tests/criterios.mjs`), and each chunk must still appear, verbatim, in the `criterio` or the `detalle` (case and final punctuation aside). If it fails («criterios 4b: nada se pierde»): a chunk lost while moving text → put it back; a deliberate clinical change → `node tests/gen-criterios-snapshot.mjs` and commit the fixture with the `data/` change; a maintenance note being retired → add it by hand to that test's `retiradas` in the fixture, leave it as a `// Nota de mantenimiento…` comment above the test, and regenerate. A hand-written sentence that only restates the generated «cuánto pesa» verdict («Sirve para descartar; un positivo es solo un hallazgo», «no puntúa») is removed from the `detalle` too (user decision, 2026-10), into `retiradas` without a comment; sentences that give a reason stay.

**Bibliographic references (`docs/referencias.md` + `data/referencias.js`):** `docs/referencias.md` is a generated index of every reference cited in `data/` (`fuente` of tests and clusters, `pronostico.fuente`, `dosisFuente`, plus author–year mentions inside other texts), grouped by reference with where each one is used (region, hypothesis, test, app phase), a «Estado de revisión» worklist, the guía-de-consulta tarjetas each region cites, and the tests with no `fuente`. `data/referencias.js` is the central registry: one entry per reference, keyed by the short form the citations use (`'Hermans 2013'`, `'Maxwell y Sterling 2013'`, `'NICE NG226'`), holding what belongs to the reference rather than to each use — `publicacion`, `doi`, and `revision` (`null` = never reviewed, or `{ fecha: 'AAAA-MM', resultado }` = last search for newer literature and its outcome). The full citation text stays in each `fuente`, unchanged (it's what the clinician sees); the app only reads the registry (lazy `import()`) to link the «Fuentes» of the «Ampliar» panels and the tissue-times card, and to fill the citation card (see «Citas» under UI Conventions). `node tests/unit.js` fails if a citation names a reference missing from the registry, if a registry entry is no longer cited, if a `revision` is malformed, or if `docs/referencias.md` is out of date — after changing any citation or the registry, run `node tests/gen-referencias.mjs` and commit the regenerated file with the change. The step-by-step review procedure (pick the first of «Estado de revisión», update every use listed for that reference reading the article itself, record `revision`) is at the top of `docs/referencias.md`. A monthly scheduled task (user's, day 1 of each month, since 2026-10) runs that review on up to 40 references: it records the «Sin cambios» ones itself and leaves every other finding as a proposal, without touching `fuente`, figures or pautas, in a draft PR «Revisión de fuentes AAAA-MM» (branch `revision-fuentes/AAAA-MM`) that the user merges; applying an accepted proposal is a manual session that reads the article, and a manual review never takes a reference an open `revision-fuentes/` PR touches. Logic in `tests/referencias.mjs`; the tarjeta/formulario footers it quotes (`TARJETAS`) are copied from guia-de-consulta by hand, since that repo isn't available to the tests. The guía-de-consulta tarjetas are extracts of regional clinical guides based on Lluch, López-Cubas, Jones, Jull, Hall y Lewis, *Pattern Recognition of Clinical Syndromes Related to Neuromusculoskeletal Pain Disorders* (ZERAPI, 2020) — registry entry `'Lluch 2020'` (`tarjetas: true`), which every «Tarjeta de consulta <región>» citation counts toward; the chapters the tarjeta footers cite (Struyf and Powell y Lewis, cap. 3; Fondevila Suárez, cap. 5) are chapters of that book. When the user supplies a regional chapter it is read in full and cited directly as `'Lluch 2020, cap. X (autor), pp.'` instead of the tarjeta (done for lumbar, cap. 5.1; cervical, caps. 5.3 and 5.3.1; hombro, caps. 3.1 and 3.1.1; cadera, cap. 4.1, subchapters 4.1.1–4.1.5; rodilla, cap. 4.2, which has no red-flag table; tobillo y pie, cap. 4.3, whose red-flag table is on p. 287; and codo, cap. 3.2 (Coombes y Bisset, pp. 81–103), which has no red-flag table and is cited directly, since codo has no tarjeta; see `docs/razonamiento-cribado.md`). A reference that `data/` cites without author–year gets `citadaComo: ['<texto>']` in the registry: Goodman, Heick y Lazaro, *Differential Diagnosis for Physical Therapists*, 6th ed., 2018 (`'Goodman 2018'`, cited as «Criterio de Goodman» in lumbar's `criterioCompuesto`).

## Commit format

Always use this format when committing:

```
git commit -m "short imperative title" -m "description when needed"
```

- First `-m` is the title (max ~72 characters)
- Second `-m` is only included when there is relevant context to add
- Never use `git commit` without flags or interactive editors
- **Never add co-authorship** (`Co-authored-by`) under any circumstance

## Pull request format

- PR body: plain description only — no `🤖 Generated with Claude Code` line, no session URLs, no co-authorship footers

### ES Modules

`index.html` loads a single `<script type="module" src="./app.js"></script>` — no bundler, no build step. `app.js` is the module root: it `import`s `state` from `state.js`, data from `data.js`, and the public functions it needs from `phase4.js`/`phase4b.js`/`lib/session.js`; `phase4.js` and `phase4b.js` import back `state`, `saveSession`, `showConfirmBanner` and (for `phase4.js`) `paintNav` from `app.js` — this import cycle is safe because those bindings are only ever called from event handlers, never at module-evaluation time.

Every file that defines functions referenced from an inline `onclick`/`oninput` attribute (in `index.html`'s static markup, or in HTML strings built by `app.js`/`phase4.js`/`phase4b.js`) must also assign them onto `window` — inline handler attributes are parsed by the browser and resolved against the global scope, never a module's private scope. `state.js` does the same for `state` itself (`oninput="state.foo=this.value"` needs `window.state`). Each file does this in one block near the bottom (`window.x = x` or `Object.assign(window, {...})`, commented `// Exposed for inline onclick...`) — when adding a new function that's called from an inline attribute anywhere in the codebase, add it to that file's block too, or the handler will silently fail (`ReferenceError` swallowed by the inline-handler call, or simply "nothing happens" on click).

`tests/unit.js` is only the entry point: it runs the topic files `tests/unit/<tema>.mjs` in order (one per area — `condiciones`, `farmacos`, `farmacos-paciente`, `puntuacion`, `payload`, `datos`, `formulario`, `cribado`, `razonamiento`, `informe-ia`, `lado-y-exportar`, `posquirurgico`, `fase5-y-version`, `revision-informe`, `verificacion`, `tejidos`, `anatomia`, `irritabilidad`, `plan-tratamiento`, `plan-ia`, `sintomas`, `citas`, `silueta`) and prints the summary; a new topic is a new file plus one line in that list. `tests/unit/comun.mjs` holds what they share: the real modules, loaded via dynamic `import()` after setting up DOM/`window`/`navigator` shims on `globalThis` (`tests/dom-shim.mjs`, see it for the exact shim set), the mini-runner `test()`, `BASE_STATE`/`withState()`, `VALID_REGIONS` and `leer(...ruta)` (reads a repo file from the root) — `globalThis.window = globalThis`, so the `window.x = x` exposure lines above also land as real globals the test file can read back. `package.json` sets `"type": "module"` so Node treats `.js` files as ES modules (still no bundler, no dependencies).

`styles.css` is intentionally kept as a single file even though it spans multiple concerns (base tokens, layout, per-phase components, responsive breakpoints). Splitting it by concern or by phase would scatter rules without a clear seam — CSS variables like `--accent` and `--surface` are used everywhere, so any split would introduce cross-file dependencies immediately. A single file also makes it trivial to grep any class and know exactly where to edit it.

## State Management

A single global `state` object (`state.js`, imported by every module) holds the entire session. There is no reactive framework — UI updates are manual DOM manipulation triggered after state mutations.

`collectPhase3()` must be called before leaving Phase 3 to persist its inputs to state.

### Phase 4b scoring (`calcLRScore`, `phase4b.js`)
There are **no default LRs**: a test with no usable LR never multiplies (the old `|| 1.5` / `|| 0.5` fallbacks were removed on purpose — they gave weight to tests with no evidence behind them). Rules:
1. Published `lr_pos`/`lr_neg` if present; otherwise computed from `sn`/`sp` when both are a single number (`LR+ = S/(1−E)`, `LR− = (1−S)/E`, badge says "(calc.)"). S/E ranges (`'52–70%'`, `'~40%'`, `'>90%'`) are not computed. An LR range (`'2.9–4.9'`) uses the bound closest to 1 (conservative). `lr_pos`/`lr_neg` must be an LR, never other text (a unit test enforces it: `'97% VPP'` was once stored as an LR− and multiplied by 97).
2. Each direction is judged separately: LR+ multiplies only if ≥ 2 (`LR_POS_MIN`), LR− only if ≤ 0.5 (`LR_NEG_MAX`). Otherwise the result is a *clinical finding*: LR = 1, counted in the label as `X/Y hallazgos compatibles`.
3. `cluster: '<id>'` on a test → it never multiplies alone; `hyp.clusters[id] = { nombre, umbralPos, lr_pos, umbralNeg, lr_neg, fuente }` does: LR+ when positives ≥ `umbralPos`; LR− only when *every* member was done and positives ≤ `umbralNeg`.
4. `tipo: 'pronostico'` (e.g. Flynn's manipulation CPR) never enters the diagnostic score.
5. With no applicable LR the label is `⚪ Sin LR aplicable · X/Y hallazgos compatibles` (`hyp-neutral`), never "Peso bajo".
6. `absorbe: [idx]` — when a composite test (e.g. rodilla's Décary groups) contributes an LR, the listed component tests stop multiplying, so the same evidence isn't counted twice.

When modifying clinical content, keep `data/` isolated from logic — this separation allows physiotherapists to review domain content independently. The content used to live in a single `data.js`; it was split **by region** (not by domain) once each region started getting its own guía-de-consulta integration: one file per region keeps diffs and reviews scoped to that region, avoids merge conflicts between sessions working on different regions, and mirrors `formularios/<region>.js`. Hypothesis ids are global: a unit test fails if two region files reuse one (`Object.assign` would silently overwrite it). `data/*.js` are static imports — if one is missing from `deploy-to-hub.yml`'s copy step the deployed app breaks entirely, which the smoke test's module check would also catch locally.

### Component classes
- `.option-btn` — single-select button groups; active state uses class `selected`. Groups with no meaningful default (`selectOption`: mecanismo, cronología, naturaleza, estabilidad, psico_*; `selectPsico`: riesgoPsico) deselect back to `''` on a second click of the already-selected option. Groups that already default to a real value (`selectSQ`/`selectSistQ`, SI/NO screening — pre-selected `NO`) don't: there's no meaningful "unanswered" state to toggle back to, so switching to the other option is already a one-click undo. ### Dialogs

The action button carries a trash icon unless `opts.borra: false`, used for actions that delete or discard nothing («Actualizar», «Pasar a completa»); the update dialog without a patient name ends its text with «…o actualiza igualmente si no la necesitas» and its button says just «Actualizar» (user decision, 2026-10). Both buttons never wrap (`white-space: nowrap`): under 480 px the box widens to a 16 px gutter and the buttons lose some padding and the cancel ✕, so the longest label («Cambiar región») fits at 320 px — a new, longer label needs a `.btn-text-short` version; the smoke test («Diálogos de confirmación») opens the dialog with every action label the app uses and checks one line, inside the box, and the trash only where it deletes; it also checks the closing rules below with real key presses and mouse clicks (Escape, scrim, dismiss button and action button; dragging from the box to the scrim; `dismiss()` twice; one dialog over another). Tapping the scrim or pressing Escape does the same as the dismiss button, never the action (only a tap that starts and ends on the scrim counts, so selecting text in the box and releasing outside doesn't close it). On ≤768 px the system Back (button or edge swipe) does the same as the dismiss button too and never changes phase — see «Back with a window open» below. It returns a `dismiss()` that closes the dialog without confirming and does nothing if it's already closed — for when what was being confirmed stops making sense (the AI generation finishing while «¿Cancelar?» is open). A new dialog replaces any open one and releases that one's scroll lock (before, two stacked dialogs left the page unable to scroll). When a scrim closes and another opens in the same tick (session panel → «Reiniciar valoración» / «Borrar sesión» / import / update dialog, and back on cancel), the new one gets class `relevo` (`_veloRelevo`, `app.js`): its scrim appears already opaque and only its box animates — fading the whole overlay in from transparent showed the unblurred page for 0.2 s (flicker). Smoke test inside «Exportar / importar».

### Back with a window open (mobile)
User decision, 2026-10: with anything open on top, the system Back (button or edge swipe) closes it and never changes phase, so a swipe can't move the phase behind an open dialog (and then confirm its action in another context). The tools, the razonamiento panel and «📤 Compartir» have their own entries (`_*Historial`); the confirm dialogs, the session panel, the phase sheet and the numeric keypad share one mechanism (`_modalAbrir()`/`_modalSoltar()`, `app.js`, only ≤768 px): opening pushes an entry, Back closes the window (a dialog = «Cancelar», `opts.onCancel` included, never the action), and closing it any other way removes the entry (`history.back()` with `_popIgnorar`), so after opening and closing any number of windows one Back changes phase as if none had opened. A window opened in the same tick as another closes (session panel → «Borrar sesión», back to the panel on cancel; a dialog to a tool on cancel) inherits the released entry (`_modalLibre` → `_empujarEntrada()` does `replaceState`); one opened while our own `history.back()` is in flight pushes when it lands (`_trasPop`). What runs after closing and navigates waits until the entry is gone: a dialog's action (`dismiss(onConfirm)`) and the phase chosen in the phase sheet (`closePhaseSheet({ despues })`). The app never reopens a window from a history entry, so a leftover entry can only be a no-op. `_closeAllOverlays()` drops the entry without touching history. Every overlay that pushes an entry must go through `_empujarEntrada()`. Smoke section `atras-ventanas`.

**Back that would close the app** (user decision, 2026-10; ≤768 px, never in the hub): in phase 1 with nothing open, Back leaves the app; with an assessment in progress or a recording it asks first, also when the patient has a name (user decision, 2026-10: guide mode's automatic name meant it never asked), and only an empty app leaves without asking. Safari and the installed app don't show `beforeunload`'s prompt, so a guard entry (`{ guarda: true }`) sits under phase 1's: `_ponerGuardaSalida()` puts it on a `click`/`input` (Chrome skips entries added without a user gesture), only at the bottom (`_historyDepth === 0`, plain phase entry) and only with `_riesgoSalida()`: recording (`body.grab-activa`, also paused) or assessment data. Back onto the guard → `_avisarSalida()`: «¿Salir de la app?» with one sentence per case (recording stops; with no name the assessment is lost; with a name it stays saved for 24 h and comes back), «Salir» / «Seguir aquí» (`showConfirmBanner(…, { sinEntrada: true, clase: 'salida-app' })`; scrim, Escape and cancel stay, re-pushing phase 1); with no risk left it just leaves. «Salir» = `history.back()` from the guard; the installed app has nothing behind, so it stays and a toast says to press Back again (`_salidaElegida`: no new guard until the next phase change, and a deeper guard left by a reload is passed through). ## Theme

Dark (default of `:root`) and light, with a manual toggle (Sistema / Claro / Oscuro). `data-theme` on `<html>` is always the *resolved* theme; light overrides the CSS variables in `:root[data-theme="light"]` (`styles.css`), so new colors must be variables, never literals (the `--header-bg`, `--nav-bg`, `--hover-tint`, `--alert-*-text`, `--lime`… tokens exist for that). The choice lives in `localStorage` (exception to the no-localStorage rule: a synchronous per-device UI preference, read by the inline script in `index.html`'s `<head>` before first paint; the IDB session expires after 24h and is async). `applyTheme()`/`setThemePref()` (`app.js`) mirror that script and follow `prefers-color-scheme` live while the choice is "Sistema". **In the hub (`window.self !== window.top`) the app is always dark** and the theme button is hidden (`.in-hub .theme-btn`) — the stored choice is ignored there even though the origin is shared. The control is a header icon `#themeBtn` (`cycleThemePref()`: one tap cycles Sistema → Claro → Oscuro, the icon shows the current choice); it was deliberately kept out of the session panel (which is about the patient/session). Hidden in the hub. The header's 🌐 translate button (`.btn-translate`) is hidden outside the hub (`body:not(.in-hub)`): it only exists as a hint for the hub embed. Every overlay (phase sheet, session panel, phase 5 share sheet, formulario previo, confirm banner) uses the same `--scrim` (background, themed) and `--scrim-blur` (6px, same on mobile and desktop), and dialogs use `--modal-shadow` — a new modal must use those tokens, not its own `rgba(0,0,0,…)`/`blur()`. The light theme sets `color-scheme: light` so native controls (checkboxes, date inputs) aren't drawn dark. Not themed: `manifest.json` colors and iOS `black-translucent` status bar (static).

## Session Persistence

IDB (`lib/session.js`) is the persistence layer for session/clinical data — no localStorage for that. The only exceptions are per-device UI preferences: the theme choice (`physiq-assessment-theme`, see "Theme"), the «Ampliar con IA» destination (`physiq-assessment-ia-destino`) and the tissue-times filter (`physiq-assessment-tejidos-filtro`).

**Write triggers in `saveSession()`** (called on every phase transition, `visibilitychange`, and all state-mutating handlers):
- `selectSQ`, `selectPsico`, `selectOption`, `updateEdadPaciente`, `updateVital` — phase 1 inputs
- `applyRegionChange`, `selectSistQ` — phase 2 inputs
- `selectNRS`, `selectIrritab` — phase 3 inputs
- `selectTreeOption` — phase 4 CIF tree
- `setTestResult` — phase 4b test results

`saveSession()` flushes DOM fields into `state` (patient, motivoConsulta, signoComparable), then calls `writeSession({ patient, date, assessmentState: { ...state } })` only if `state.patient` is non-empty. Navigating phases without a patient name does not write to IDB; `SESSION_ASSESSMENT_PARTIAL` is still emitted by `goToPhase()` for real-time report sync.

**Ghost-write protection** — two guards prevent a stale `writeSession` from recreating a deleted session:
- `_sessionGen` (integer) — incremented on every clear. Captured before the async `writeSession` call; if `_sessionGen !== gen` at resolve time, `clearSession()` is called to undo the stale write.
- `_sessionCleared` (boolean) — set `true` synchronously on clear; blocks `saveSession()` from starting a new write until `state.patient` is non-empty, then resets to `false`.

**On startup:** `readSession()` checks for `session.assessmentState.maxVisitedIdx > 0`. If found, silently restores all state via `_restoreSessionDOM()` and `goToPhase(targetPhase)`. No prompt. Note: `assessmentState` is only persisted when a patient name is set, so startup restoration only applies to prior sessions where a patient name was entered.

**Session button** in the header (`#sessionBtn`) is a person-silhouette SVG icon. Opening the panel doesn't focus the patient-name field (user decision, 2026-10: on a phone it brought up the keyboard when the panel is usually opened to export, import, check the version or clear; smoke test). The panel's trash button triggers `promptClearSession()`, which closes the panel and opens the common centred dialog (`showConfirmBanner('Borrar sesión', …)`, naming the patient and the audio if any); confirming runs `_borrarSesion()` → `_softResetApp()` + `goToPhase(1)` + `clearSession()`, cancelling (button, scrim or Escape, via `opts.onCancel`) reopens the session panel; it also empties `#patientName`, which stays in the DOM and would otherwise bring the name back through `saveSession()`. The smoke test (inside «Exportar / importar») checks all of it, including the escaped name.

**Export / import (`.json`)** — the session panel has «⬇ Exportar» and «⬆ Importar» under the patient field (two equal-width buttons that fit at 320 px, plus a one-line note that the file holds clinical data and the patient's name), meant for repeating tests with the same data (e.g. regenerating the narrative report after a prompt change). Export (enabled once past phase 1, `maxVisitedIdx > 0`) calls `saveSession()` to flush the DOM fields, then downloads `valoracion-<paciente>-<AAAA-MM-DD>.json` = `{ app, tipo, version, exportado, assessmentState }` — the whole `state`, patient name included, **without** `informeIA` or `planTratamiento.ia` (the point is to regenerate them) or the audio; on touch devices it uses the share sheet when `navigator.canShare({ files })`, otherwise an `<a download>`. Import (`#sessionImportFile`) validates with `leerImportacion()` (bad file → toast, nothing changes), asks with `showConfirmBanner` (mentions the audio via `_avisoAudioSesion()`), then `_aplicarImportacion()`: sets `_importando` (makes `saveSession()` a no-op, since the DOM still holds the old assessment and a `visibilitychange` during reload would otherwise overwrite the import), discards the session audio, `clearSession()` (no leftover `assessment`/`rom`), `writeSession({ patient, date, assessmentState })` and `location.reload()` — the existing startup restore does the rest. Unit tests cover the round trip and the rejections; the smoke test exports, clears, imports and checks the state comes back in phase 5, and that the buttons fit at 320 px.

**Deployed version** — so the clinician can tell, after a merge, whether the deploy has reached this device. `deploy-to-hub.yml` («Stamp deployed version») replaces the two `export const` lines of `lib/version.js` in the hub copy with the short commit SHA and the UTC deploy time, and writes `version.json` with the same `{ sha, fecha }` (the step fails if the substitution didn't happen; a unit test pins those exact lines). The session panel ends with «Versión a1b2c3d · 7 oct, 14:32» (`#sessionVersion`; the year only when it isn't the current one; «dev» locally): one line, text on the left and a single button on the right: «Comprobar», or with a newer version «Actualizar» filled in blue like the pill's button (`.session-version-btn-nueva`; «Comprobar» stays outlined, same label and action as the pill's button; no extra text — the pill already explains, and the button's `title` says whether it's still being published); neither the version nor the date breaks in the middle, so it fits at 320 px. `comprobarVersion()` (`app.js`) fetches `./version.json` with `cache: 'no-store'` at startup, whenever the app becomes visible again (at most once a minute; never with `'dev'`) and from the panel's «Comprobar» button (`{ manual: true }`: no throttle, always a toast — «✓ Estás en la última versión» or the error); if its sha differs from the loaded one, a «Hay una versión nueva · Actualizar» aviso appears (`#versionAviso`) and the panel's button turns into a filled blue «Actualizar». On desktop it is a pill under the fixed header; on ≤768 px (user decision, 2026-10: the floating pill covered the phase title and was small for a finger) it is a full-width snackbar (16 px gutters, 0.9rem, 44 px touch targets) just above the fixed navigation buttons — `_colocarAvisoVersion()` measures the active phase's `.nav-buttons` into `--nav-alto` (on show, `goToPhase` and resize) — so it never meets the phase 2/4b context bars at the top; it hides while a text field has focus (the keyboard moves the bottom bar). Under 380 px the text is «Versión nueva» instead of «Hay una versión nueva» (`.version-aviso-largo`/`-corto`), so it stays on one line next to the 44 px button and `×`; while reloading (`_avisoActualizando()`, called by `recargarVersionNueva()`) the aviso becomes a status line «⟳ Actualizando…» (`.version-aviso-actualizando`, `aria-busy`) with no button or `×`, since neither does anything then, and the panel's button says «Actualizando…» too. `×` hides it for that sha and leaves a blue dot on the session icon (`#sessionBtn.version-nueva`, `_puntoVersionSesion()`) until the version is current, since the panel has the «Actualizar» button. The smoke test («Aviso de versión nueva») stamps a fake deployed version with `page.route` and checks the position in every phase (also with the phase 2 context bar), the touch targets, 320 px, one line at 320/360/390 px before and while updating, hidden while typing, the dot after `×`, and the desktop pill. **No `?t=` cache-buster on `version.json`**: it must come from the same server/CDN state as the code — with a unique URL it arrived new while `lib/version.js` still came from a cache, so the pill reappeared after every reload (reproduced with `max-age=600` and no service worker). `recargarVersionNueva()` saves the session, re-fetches every same-origin `.js`/`.css` the page loaded with `cache: 'reload'` (from `performance.getEntriesByType('resource')`, max 4 s, plus `registration.update()`) so the browser's HTTP cache can't serve the old code, then reloads; it asks first when there's assessment data and no patient name, since that session isn't persisted. It notes the sha it reloaded for in `sessionStorage` (a per-tab UI flag, try/catch): if after reloading that same version still hasn't arrived, the pill (and the panel button's tooltip) say «La versión nueva aún se está publicando: prueba en unos minutos» instead of repeating «Hay una versión nueva». `sw.js` never caches `version.json`, and fetches the app's own subresources with `cache: 'no-cache'` (revalidation, 304 when unchanged) so a reload after a deploy doesn't keep serving `app.js` & co. from GitHub Pages' 10-minute HTTP cache.

**`↺ Reiniciar valoración completa`** (button «Reiniciar valoración» `#sessionReset` in the session panel, under the patient field, disabled without assessment data — moved out of the header, user decision 2026-10: destructive and rare, it doesn't need a header slot; like «Borrar sesión», it closes the panel while asking and reopens it on cancel; calls `resetApp()`) resets all clinical data (phases 1–5) but **preserves `state.patient` and `#patientName`**. Under its note, a closed «¿Reiniciar o borrar?» (`<details class="session-ayuda">`, `_ayudaReiniciarBorrarHTML()`; user request, 2026-10) explains the difference with «Borrar sesión»: what each keeps (name, the stored session, the consultation mode), what both erase, that Borrar also clears other tabs and the hub copy, and — only outside the hub — that the assessment lives only in this browser (24 h, with a name) and «⬇ Exportar» keeps it. On ≤768 px `#sessionPanel` has `max-height: 90dvh` and scrolls inside (the swipe-to-close only listens on its top 72 px), so the open help fits a short screen (smoke, «Exportar / importar») — the patient identity survives a clinical reset, consistent with the pattern in physiq-motion, physiq-force, and physiq-balance where "borrar mediciones" never clears the patient name.

## BroadcastChannel protocol

All satellites use `const _sessionCh = new BroadcastChannel('physiq-session')`.

Messages emitted by physiq-assessment:

| Type | When | Payload |
|------|------|---------|
| `SESSION_PATIENT` | after each IDB write or reset | `{ patient: string }` |
| `SESSION_ASSESSMENT_PARTIAL` | on every `goToPhase()` call | `{ phase: string, region: string \| null }` |
| `SESSION_ASSESSMENT` | in `registrarValoracionCompleta()` only (every option of phase 5's «📤 Compartir» menu) | `{ assessment: buildPhysiQPayload() }` |
| `SESSION_CLEAR` | after `promptClearSession()` full clear | — |

`SESSION_ASSESSMENT_PARTIAL` is emitted **before** `saveSession()` in `goToPhase()`, synchronously, for all phases including phase 5. physiq-report uses this to display an "incompleto" badge in real time.

## Phase 5 and finalizarValoracion()

Reaching phase 5 (`buildResults()`) renders the summary HTML but does **not** emit the assessment payload. `registrarValoracionCompleta()` (`app.js`, exported) does: `buildPhysiQPayload()` (including `pn: state.planNotes`), `writeSession({ assessment: payload, patient, date })` — physiq-report reads it from IDB on its own load, so it's never wasted — and `SESSION_ASSESSMENT` via BroadcastChannel (a harmless no-op when nothing listens).

Every option of phase 5's «📤 Compartir» menu calls it first, in and out of the hub. ## Modo breve

Consultation type chosen at the top of phase 1 (`#modoConsulta`, `selectModo()`): **Completa** (default; old sessions without `modo` stay completo) or **Breve (10')** for insurer visits. Design and the 5 clinical decisions behind it: `docs/modo-breve.md`. Rule that never bends: **breve never hides a safety item** — phase 1 red flags, questions with `urgencia`, the region `urgencia` box, the urgent-referral alert and the full CIF tree work exactly as in completo. Breve only folds optional fields and makes the gaps explicit.

- **«⏱ Breve» chip** (`.modo-badge`, view only): in the header on desktop; on ≤768 px it moves to the start of the mobile phase bar (`.modo-badge-fase`, user decision 2026-10: it is the consultation's state, not an action, and the header was crowded) and keeps the word «Breve» there even on narrow screens.
- **Mobile phase bar** (`#mobilePhaseBar`): the whole bar is one `<button>` that opens the phase sheet (`togglePhaseSheet()`, `aria-expanded`), with a borderless «≡» as the hint (user decision, 2026-10: bigger touch target than the old bordered «≡ Fases» button). Smoke test («barra de fase en móvil»).
- `body.modo-breve` (set by `_pintarModoUI()`) drives everything visual via CSS: `.breve-opcional` is hidden (vitals except age, `psico_*`, the irritability matrix, naturaleza/estadio/estabilidad), `.breve-only`/`.breve-only-inline` are shown. `toggleBreveVerTodo()` (`body.breve-ver-todo`, view-only, not persisted) shows everything again, including the folded phase 2 questions — that's how pending items get completed without leaving breve.
- **Phase 2 embudo**: `buildSistemaHTML` adds one SÍ/NO per system (`[data-embudo]`, `selectEmbudo()`) read against that system's `banderasRojas`, and wraps the questions in `.sis-body`. With the embudo not in SÍ, CSS hides every `.sq2` **except `.sq2-urg`** (questions with `urgencia`) — a unit test checks every urgent question carries that class and no other does, and the smoke test checks it in a real browser. NO is refused while the system has any SÍ answer; a SÍ answer flips an embudo NO to SÍ. Unanswered questions stay `'NO'` as always — `sistemicoBreve` is what tells "asked one by one" from "screened by embudo".
- **Phase 3**: `selectIrritabDirecta()` sets `irritabilidadNivel` directly and `irritabilidadDirecta: true`; a hint under it names the key question (time to settle, `TEXTOS_IRRITABILIDAD.pistaBreve`); touching the matrix (`_usarMatrizIrritabilidad()`) switches back to the computed level. Summaries say "(estimada)".
- **Phase 4**: `#btnSinConfirmar` ("Resultados sin confirmar →", breve only) goes to phase 5 skipping 4b; greyed out by CSS while `#btnGoConfirm` is disabled (`#btnGoConfirm:disabled ~ #btnSinConfirmar`), so no change to `phase4.js`.
- **Phase 4b**: `buildTestList()` lists first the tests that can move the score (`testPuntua()` — same rules as `calcLRScore`, a unit test cross-checks both) and folds the rest in `<details class="breve-hallazgos">`. Visual order only: every test keeps its index in `state.testResults`.
- **Pending items**: `getPendientesBreve()` → `[{ texto, fase }]` (systems by embudo, systems not screened, estimated or unregistered irritability, active hypotheses with no pos/neg test, empty formulario previo); `[]` in completo. Shown in phase 1 (`#brevePendientes`, once past phase 2, with "Completar pendientes →"), at the top of phase 5, in `📋 Notas`, and in the payload (`pe`).
- **Transparency**: `TEXTO_VALORACION_BREVE` goes into phase 5, `📋 Notas` and `📄 Informe` in breve, always (decision 3 of the design); the Informe's "IMPRESIÓN CLÍNICA" says "(hipótesis de trabajo, pendiente de confirmar)" when tests are pending. Switching breve → completo with pending items asks for confirmation, because from then on the summaries stop saying the assessment was brief.

## Formulario previo

Pre-visit form transcribed from guía-de-consulta (`tools/plantilla_formularios.js` cara 1 + `data/formulario_<region>.js` cara 2) — question text kept literal (except codo's cara 2, `formularios/codo.js`, designed in PhysiQ from Lluch 2020, cap. 3.2, since guía-de-consulta has none; user decision, 2026-10: anabolic steroids, which the chapter asks about, are left to the in-person interview); the paper header (name, date, age) is not repeated because phase 1 already has it. The physio fills it in PhysiQ, inline (no modal): the general half is a `<details class="fp-details">` card (`#fpDet_comun`) in phase 1 right after the motivo, and the regional half is its own `<details>` (`#fpDet_region`) in phase 2, after the urgency box and before the screening notes/systems — it is a *pre-visit* form, so it stays ahead of the red-flag questions, but separate from them. Both start closed and are painted on open (`fpToggle`, via `ontoggle`); `_refrescarInline()` repaints the open ones on region change, reset and session restore. Each summary shows its own counter (`#fpCont_comun`/`#fpCont_region`, `_contarScope()`: every answered row of a `matriz` counts as one answer, so the counter moves with each row); titles use the `.card-title` style on one line («FORMULARIO PREVIO · GENERAL», «… · TOBILLO Y PIE» via `#fpNombreRegion`), with the counter on the right (below the title under 480px). A region without a `formularios/<region>.js` (today: none — every region has one) shows a warning alert inside its details instead of the form. `abrirFormularioPrevio('comun'|'region')` (exported to app.js) opens one and scrolls to it — used by "Completar pendientes →" in modo breve. Every `texto` item gets the same mic + chips bar as `motivoConsulta` (`injectQuickInputBar(fieldId, chips)`, exported from `app.js`); the chips come from the item's own `chips` in the schema. Answers linked through `pistas` show as a "📝 Refiere el paciente" box (dashed border — reserved for the patient's voice; free-text answers and option `detalle` text in italic «quotes», as a literal citation; option answers without quotes since they are the paper form's wording, not the patient's; the form tells the physio to write free text in the patient's own words (`.fp-literal-nota`)) inside the matching CIF step (`renderStep` → `pistasPasoHTML()`, `phase4.js`: `window.fpPistasPaso` plus the phase 3 symptoms linked to the step, painted by `pistasHTML()`, `lib/pistas.js`) — a reminder only, never an automatic answer. The same box also shows in phase 1 on top of the Mecanismo de Inicio and Cronología cards (`#fpPistas_mecanismo`/`#fpPistas_cronologia`, from `formularios/comun.js`'s own `pistas`, painted by `_actualizarPistasFase1()` alongside the counters): phase 1's order is Motivo → Formulario previo → Mecanismo → Cronología → Signos vitales, so the patient's own account of onset ("1 · Cómo empezó") sits right above the clinician's classification of it. Never preselect those cards from the form — `desde_cuando` is free text and Post-quirúrgico has no counterpart. The `📄 Informe` (patient/GP, `buildInformeFisioterapiaText()`) never dumps the whole form: only items with `informe: '<etiqueta>'` in the schema go in, as `etiqueta: respuesta` lines under "SEGÚN REFIERE EL PACIENTE", or under "ANTECEDENTES REFERIDOS POR EL PACIENTE" when the item also has `antecedente: true` (enfermedades, operaciones, medicación). `informeFormularioPrevio()` (`formulario.js`) builds both lists: it skips "No sabría decir" and hidden (`mostrarSi`) items and joins consecutive items sharing a label into one line (actividad_1..3). Chosen per question with the clinician: common (onset date, prior episodes, trend, night pain, limited activities, treatments tried, health history), lumbar (leg radiation, weakness), cervical (arm radiation, weakness, headache, dizziness — yes/no only), hombro (previous dislocation), tobillo_pie (injury mechanism, previous sprains of the same ankle); codo (injury mechanism, snap at the time of injury, immobilisation); cadera and rodilla send nothing region-specific. Never mark a `matriz` (unit test). The paper sheets' own title and intro («Antes de su primera visita», «Sobre su espalda en concreto», «Marque lo que mejor describa…») aren't in the schemas either (user decision, 2026-10): they spoke to the patient before the visit and repeated the `<details>` title, so `formulario.js` paints one physio-facing hint for both halves («Si el paciente no lo sabe, marque «No sabría decir» o «No sé»…»). Nor the sections' paper navigation («Si NO tiene dolores de cabeza, salte este apartado y vaya a MAREO», «Si en la hoja 1 contestó…», «…ha terminado»): where a gate question exists `mostrarSi` already hides the rest, and otherwise the section title says when it applies («Si empezó con un golpe…», «Si hace deporte o ejercicio»); a regional section is never hidden by an answer of the general half (user decision, 2026-10). The paper form's last box («prefiero comentarle en persona») is deliberately not in `formularios/comun.js`: the physio always fills the form with the patient present, so it added nothing and leaked a content-less confidence into `📋 Notas`/physiq-report; old sessions that stored `en_persona` are harmless — summaries only walk items that exist in the schema. Deploy: `formulario.js` and `formularios/` must be in `deploy-to-hub.yml`'s copy step.

## Paciente posquirúrgico

Design and the 8 clinical decisions: `docs/posquirurgico.md`. Common to the 7 regions, **no protocols per type of surgery**: the surgeon's protocol rules.

- **Tarjeta «Cirugía»** (`#cardCirugia`, phase 1, right after Mecanismo): shown only with mecanismo Post-quirúrgico, via `body.posquirurgico` (`_pintarCirugiaUI()`, CSS `.solo-posq`). Intervención (mic), fecha (or `semanasAprox` if unknown; `semanasCirugia()` computes weeks on the fly), protocolo Escrito / Verbal / No hay (`selectCirProtocolo`), restricciones (mic), complicaciones as a closed list + «otra» (`toggleCirComplicacion`; «Ninguna» is exclusive). Not folded in modo breve. Data survive a change of mecanismo but no summary reads them unless it's Post-quirúrgico.
- **Protocol rules the plan**: phase 5 opens with a «Paciente posquirúrgico» box (`_cirugiaResultadosHTML`); every guideline pauta gets «Solo si es compatible con el protocolo del cirujano…» (`TEXTO_PAUTA_COMPATIBLE`); `📋 Notas` gets a «🏥 CIRUGÍA:» line; `📄 Informe` an «ANTECEDENTE QUIRÚRGICO» block and a first PLAN line; the AI report a «Cirugía» data block plus a `REGLAS_COMUNES` rule. Without a protocol (`conProtocolo()` false: «No hay» or empty) all of them say «Restricciones pendientes de confirmar con el cirujano», and modo breve lists it as a pending item (`ancla: 'cardCirugia'`).
- **«Ya diagnosticada y tratada»** (any mecanismo — a cast-treated fracture or treated gout has the same problem): checkbox on every active `DOSIS_DERIVAR` hypothesis — and, with mecanismo Post-quirúrgico, on **every** tree hypothesis as «Tratada con la cirugía» (`admiteTratada()`; e.g. `ca1` artrosis after a hip replacement); if the mecanismo changes, a non-«Derivar» mark is kept but stops counting, and `sincronizarTratadas()` (called from `selectOption('mecanismo')`) restores its test score —, in its 4b card and its phase 5 card (`casillaTratadaHTML`, `toggleDiagnosticoTratado`; `esTratada`/`marcarTratada` in `phase4b.js`). Marked: its tests fold and don't score (label `ETIQUETA_TRATADA`, answers kept), no «🚑 Derivación» in phase 5, no pending tests in breve, `dt: true` in the payload, «(intervenida quirúrgicamente)»/«(diagnosticada y tratada)» in the Informe, and the AI report neither refers it nor lists its tests. The same checkbox sits under a `resoluble` tree referral (`toggleDerivacionArbolResuelta`, `phase4.js`); a new answer on that step forgets the mark. Marking never hides a phase 2 urgency.
- **Generic post-surgical hypothesis `pq1`** (`HIP_POSQUIRURGICA`, `data/comun.js`): with mecanismo Post-quirúrgico it is always the first hypothesis, never from the tree. It is **not** in `HYPOTHESES` (that holds the regional ones, and their integrity tests require a region and tests) nor in `state.activeHypotheses` (tree only): `hipotesisActivas()` (`phase4b.js`) prepends it, and `hipotesis(id)` resolves it with the name «Postoperatorio: <intervención>» (or «Rehabilitación posquirúrgica») and the region's PROM (`promPorRegion`, each one a PROM the region's hypotheses already use — unit test). Anything listing the active hypotheses (4b cards, phase 5, payload `h[]`, `📋 Notas`, `📄 Informe`, `construirAmpliado()`) goes through `hipotesisActivas()`/`hipotesis()`; `getPendientesBreve()` and `clearAllTests()` keep reading `state.activeHypotheses`, so `pq1` is never a pending item. No tests or score (`ETIQUETA_HIP_POSQ`), pauta = the surgeon's protocol (`pautaHipPosq`: «Seguir el protocolo del cirujano: <restricciones>», or `TEXTO_SIN_PROTOCOLO`). Changing the mecanismo, intervención, protocolo or restricciones empties `#hypothesisCards` (`_invalidar4b()`) so 4b rebuilds.
- **Trauma questions** (`notaPosquirurgica: true`: `h_t1`, `co_t1`, `co_t2`, `ro_t2`–`ro_t4`, `tp_t1`, `cv_ar3`; unit test pins the list): a `.nota-posq.solo-posq` line under the question, logic unchanged.
- **Phase 2 post-surgical screening** (`SIS_POSQUIRURGICO`, id `transversal_posquirurgico`, `data/comun.js`): first system of all 7 regions (same object), but `soloPosquirurgico: true` — `sistemasActivos()` (`app.js`) shows it only with mecanismo Post-quirúrgico and keeps only each region's questions (`regiones` on a question; none = all). Everything that reads the screening (alert, urgencies `ur`, `sq`, embudo, breve pending items) goes through `sistemasActivos()`/`_respuestasActivas()`, so an answer of a hidden system never counts; changing the mecanismo with phase 2 already painted calls `_repintarCribado()` (also used by session restore), which keeps the answers. Questions: `pq_herida`, `pq_tvp` / `pq_tvp_ms` (hombro, codo), `pq_tep`, `pq_compart` (codo, rodilla, tobillo_pie), `pq_sdrc` and `pq_nervio` (limb regions), `pq_nervio_col` (lumbar, cervical: new deficit after spinal surgery, epidural haematoma; Fase M); all urgent except `pq_sdrc`. Sources (free, not Goodman): Zabaglo 2024, Wang 2020, Schroeder 2017, Finucane 2020, NICE NG125, NICE NG158, NICE NG89, Vyas 2024, Guthmiller 2025, Goebel 2018 (RCP CRPS guideline), Torlincasi 2023. Reviewed by the user (2026-10); follow-up in `MIGRATION_PLAN.md`, Fase G.

## Informe narrativo con IA (standalone)

Only when the app runs **outside the hub** (`body:not(.in-hub)`): at the end of phase 5, `buildResults()` calls `_montarInformeIA()`, which `import()`s `informe-ia.js` and paints the card into `#informeIA`. In the hub it returns before the import (unit test), so the module is never even downloaded — there the narrative report is physiq-report's job. physiq-report itself is **not** modified: the card calls the existing orchestrator route `POST /` of the worker that lives in physiq-report's `workers/` (`ORCHESTRATOR_URL`), exactly as physiq-report does.

Full record (every prompt and review rule with the report review that motivated it): **`docs/informe-ia.md`**. Read it before changing the prompt or the review rules.

- **Licence** (`lib/licencia-ia.js`, shared with the recorder): at startup, `GET /validate` with `localStorage['physiq-license-key']` (the key the hub saves; shared per origin). The worker decides the mode, never the client: unless `routes.report === 'real'` the card is disabled («Disponible con licencia PhysiQ») with an «Introducir clave» link — the typed key is validated first and only stored if the worker says `real` (a bad key never overwrites the hub's). `demoOnly` → «desactivada temporalmente». When `/validate` gives no usable answer the card says «No se ha podido comprobar la licencia» plus the reason (`detalleLicencia()`): timeout, offline, HTTP 429/5xx (an error status is never read as «sin licencia»), or — since a failed `fetch` can't tell a blocker from a worker error without CORS headers — a second `mode: 'no-cors'` probe without the key: reachable → «el servidor responde, pero con un error», unreachable → blocker/network. One automatic retry after 1.5 s before showing it. A generation response with `X-PhysiQ-Mode: demo` is **discarded** and the card goes back to «sin licencia»: the worker's demo fixture is a fictional patient and must never sit next to a real assessment.
- **Turnstile** (required by the worker in real mode): `lib/turnstile.js`, one widget per AI card (this one and phase 6's «✨ Detallar con IA») and one script for the page, loaded only once a card is licensed (`?render=explicit`), same sitekey as physiq-report; one token per request, reset after use. `challenges.cloudflare.com` is network-only in `sw.js`.
- **Audio** (optional; `grabadora.js`, `lib/audio-store.js`): recorded from the **header** (`#grabBtn`, any phase — the consultation happens in phases 1–4b; shown only with `body.ia-licencia` or `body.grab-activa`), never as a floating widget, since on mobile it would cover content. One session = one recording, no manual «Parar»: tap starts; then the pill «● 12:34» pauses/resumes on tap and a long press (`LARGO_MS`), or the trash `#grabDescBtn` with a mouse, asks to discard (`showConfirmBanner`). On mobile, going to the background pauses it (`pausaAuto`, the system stops giving audio there). It closes itself and becomes the session audio on «Generar informe» (`cerrarGrabacion()`), at the 25 MB cap (Whisper), when the system ends the mic track, or after `PAUSA_MAX_MS` (20 min) paused. Chunks go to IDB every 10 s, so a reload recovers it. Silence detection (`silencioDetectado()`, `UMBRAL_SONIDO`) warns when a muted or wrong mic records nothing. The phase 5 card shows the recording, the finished audio or «📎 Adjuntar audio». Deleted after generating, on «Quitar», and only on resets **confirmed on this device** (`resetApp()`, «Borrar sesión»), never from `_softResetApp()` itself (relayed resets; unit test). Not automatable: a real phone mic, iOS/mp4, system interruptions, the 20-min close. Details: `docs/informe-ia.md`.
- **Consulta o dictado** (`MODOS_AUDIO`, `#iaModoAudio`, only with audio): «Consulta (diálogo)» (default) or «Dictado del fisioterapeuta», where the physio narrates the consultation at the end. Whisper doesn't separate voices, and dictation fixed the misattributions of the dialogue. In dictado the transcript block and `reglaAudio()` change (first person = physio; what they say wasn't done doesn't appear at all), the Whisper hint gets a prefix (`getWhisperPrompt(region, { dictado })`) and `state.informeIA.dictado: true`. Under 480 px the card's two selectors are two equal columns (`MODOS_AUDIO[k].corto`/`.sub`; smoke test at 320 px).
- **Consent**: with audio, a mandatory checkbox («El paciente ha sido informado y consiente…») — not persisted, asked again for every audio. A privacy note above the button says data and audio go to OpenAI and Anthropic through PhysiQ's server.
- **Prompt** (`PLANTILLAS` in `lib/informe-narrativo.js`): two templates, adapted copies of physiq-report's — **Narrativo** (`buildNarrativePrompt`, `PALABRAS_INFORME` 2000, ends in `SEGUIMIENTO FUNCIONAL`) and **Ficha breve** (`buildFichaBrevePrompt`, `PALABRAS_FICHA` 700, ends in `OBJETIVOS Y PLAN`, CIF codes only from the closed list `CODIGOS_CIF`). Default by consultation type (`plantillaPorDefecto(state.modo)`); `informeTruncado()` checks the last section. Rules common to both apps live in `lib/reglas-informe.js` (byte-identical in physiq-report, SHA-256 pinned in both repos). The data block is the payload **plus datos ampliados** that `buildPhysiQPayload()` must not carry (`construirAmpliado()`/`bloquesAmpliados()`, `informe-ia.js`; unit test). Prompt-only texts exist so screen labels aren't read as this patient's findings: `iaPregunta`/`iaTexto`/`iaEntera` on tree steps and options, `textoOpcionIA()` (only the option's conclusion before « — »), `iaTexto` on form matrix rows; prognostic rules (`tipo: 'pronostico'`) go in their own block; with an urgent referral (`ur`) no pauta is sent. **Every rule was added after a failure in a real report review (rounds 1–29)** — the full list of rules, what each one fixed and the reports it came from are in `docs/informe-ia.md`; read it before changing the prompt, and add a new rule there with the failure that motivated it. Review a prompt with `tools/prompt-desde-json.mjs`.
- **Revisión automática** (`lib/revision-informe.js`, `pintarRevision()` in `informe-ia.js`): every time the result is painted, the report text is checked against the current data (and the transcript) and `#iaRevision` shows «⚠ N puntos a revisar» (`alto`/`medio`, each with the quoted sentence) or «✓ Sin incidencias». Each rule comes from a failure seen in a review (referrals or hypotheses not mentioned, side/age/sex contradicted, NRS figures invented or given a moment, sources named, prognostic rules used as support, discrepancies split, invented frequencies, sections out of order…; full list with examples in `docs/informe-ia.md`). They are «points to review», never a score, never block or change the report, never reach the payload or summaries; a rule that throws leaves the box empty. Below it, the fixed «☑ Antes de compartir, comprueba:» box (`comprobacionesManuales()`) lists the serious failures no text rule sees. Every point and check has a «Revisado» checkbox (`iaMarcarRevisado()`; dimmed, never hidden; «revisado» = «I looked at it»), stored in `state.informeIA.revisados` by `clavePunto()`/`claveComprobacion()`, so a point that disappears loses its mark. The card's own controls don't count as assessment changes (`_refrescarHuellaDiferido()` ignores `input` inside `#informeIA`). When adding a rule, add a real report to the fixtures (see Tests below).
- **Revisión con IA (capa 3)** — **parked** (user decision, 2026-10), not in the card: a second model fills extraction lists (`ESQUEMA_VERIFICACION`, `lib/verificacion-informe.js`, worker route `POST /verify`) and points are derived in code (`puntosDeExtraccion()`, `validarPuntos()`). Measured with `tools/verificar-informe.mjs` against `tests/fixtures/informes/esperado-capa3.json`: Sonnet ×3 detected 32 % of known failures with ~3.4 unlabelled points per report, below the agreed bar (≥ 50 %, 3/4 `alto`, ≤ 1 unlabelled point). Code, tool and fixtures stay for a later attempt; criteria, rounds and the plan if it passes are in `docs/informe-ia.md`.
- **Errors from the APIs**: the worker forwards them as «Whisper: …» (OpenAI) or «Claude: …» (Anthropic), in English. `errorLegible()` (`lib/informe-narrativo.js`) maps them by keyword families — no saldo/cuenta, clave inválida, saturado, audio no válido (Whisper only), servicio caído — to a Spanish message naming the service, with a generic per-service fallback; messages without that prefix are our own and pass unchanged. The card keeps it on screen (`#iaError`, until the next attempt or a reset) with the original text below, and for a transcription failure suggests generating without audio (the audio is kept). Unit-tested with the real API messages.
- **Transcript with no voice**: on silent audio Whisper returns filler («Subtítulos realizados por la comunidad de Amara.org», «Gracias por ver el vídeo»…) and the report ignored the audio. `transcripcionSinVoz()` (`lib/informe-narrativo.js`: empty, under 4 words once the known filler is stripped, or one sentence repeated) is checked on the SSE `transcript` event, only with audio: it throws `SinVoz`, the stream is aborted before the report is written, no report is saved, the audio is kept, and `#iaError` shows `TEXTO_SIN_VOZ` (check the mic, record again or generate without audio). Unit-tested with the real filler.
- **Screen off / app in background while generating**: generation is a 1–3 min streaming request, and a mobile browser suspends a hidden page and cuts its connections (screen auto-lock, manual lock, switching apps), so the stream fails with a network `TypeError` («Load failed», «Failed to fetch»…). `iaGenerar()` therefore holds a screen wake lock while generating (re-requested when the page becomes visible again, released in `finally`), shows «Mantén la pantalla encendida…» (`.ia-nota-pantalla`) under the progress line, notes `_gen.oculto` if the page was hidden, and `errorConexion()` (`lib/informe-narrativo.js`) turns that network failure into «Se ha cortado la conexión porque la pantalla se apagó…» (or «Se ha perdido la conexión…» if the page never went hidden) instead of the raw browser text — only for a `TypeError` with a network message, never for an API error or a code bug (unit test). The audio is kept, so «Generar» again just works. A manual lock can't be prevented from a web page; surviving it would need a resumable job on the worker (physiq-report), not done.
- **Result**: streamed (SSE `transcript` → `report_chunk` → `done`) with a progress line led by the template (`_gen.plantilla`, `seccionLegible()`) and a closed «Ver mientras se escribe». «Cancelar» asks first (`iaCancelar()`, `cancelLabel: 'Seguir'`; the dialog closes itself when generation ends). Saved in `state.informeIA` (persisted with the session, i.e. only with a patient name), rendered folded in `<details id="iaResultadoDet">`; the card's only action is «Descartar» — sharing is phase 5's «📤 Compartir» → «Informe clínico (IA)» (local header + «redacción asistida por IA» footer, `textoParaCompartir()`). `huella` (FNV of payload + datos ampliados, minus the date) warns when the assessment changed after generating. Never part of `buildPhysiQPayload()`, `📋 Notas` or `📄 Informe` (unit test).
- **«⬇ Paquete de revisión»** (small grey link after «Descartar», visible to every clinician): `iaPaqueteRevision()` downloads `revision-informe-<paciente>-<fecha>.zip` (`lib/paquete-revision.js` + `lib/zip.js`, loaded with `import()`): `info.txt` (versions, template, audio mode, huella, the two review commands), the report as shared, the transcript, `revision.txt` (points in `tools/revisar-informe.mjs`'s format, «[revisado]» marks), `valoracion-<paciente>.json` (importable) and `prompt.txt` (`state.informeIA.prompt`). Holds clinical data. Never in the hub; a unit test checks every `.js` of the root or `lib/` the app imports (plus `app.js`, `data/*.js`, `formularios/*.js`) is in `deploy-to-hub.yml`.
- Tests: `tests/fixtures/informes/` holds real reports (exported assessment + report + transcript; table in its `LEEME.md`, case history in `docs/informe-ia.md`). `tests/unit.js` («revisión: informes reales», table in `tests/unit/revision-informe.mjs`) runs each through `revisarArchivos()` and pins the exact list of points, so a new or changed rule can't drop a hit or add a false positive unnoticed — **when a report is reviewed in a session, add it there**. «informe narrativo» covers the pure functions (`tests/dom-shim.mjs` stubs `fetch`); `tests/smoke.mjs` runs the whole card with the worker and Turnstile mocked by `page.route` (no API cost), records with Chromium's fake mic, and checks none of these modules loads in an iframe.

**In the hub** this satellite records nothing: the `RecorderEngine` lives in the PhysiQ hub (`physiq/index.html`) and persists across all satellites. physiq-assessment runs inside an iframe in the PhysiQ hub. On load (`_initHubIntegration()` in `app.js` — moved there from an inline `<script>` in `index.html` during the ES modules migration, since it needs direct access to module-scoped state like `_historyDepth`):

```js
if (window.self !== window.top) {
  document.body.classList.add('in-hub');
  document.querySelector('.logo-main').addEventListener('click', () => {
    window.parent.postMessage({ type: 'PHYSIQ_GO_HOME' }, '*');
  });
}
```

CSS `.in-hub .logo-main` adds a `‹` back-arrow hint. When running in-hub, clicking the logo navigates back to the hub home.

`showConfirmBanner` sends `{ type: 'PHYSIQ_WIDGET_HIDE' }` to the parent when opening and `{ type: 'PHYSIQ_WIDGET_SHOW' }` when closing, so the hub recorder widget is hidden during modals.
